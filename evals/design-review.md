# 设计工作流评审场景

用于评审描述选择、按需读取、设计深度与实施续做。以下是场景及判据，不是通过记录，也未接入 `run.py` 的自动评分。实际执行情况见 [验证记录](VALIDATION.md)。每个场景用独立的临时项目和新会话，保留原始输入、实际产物、过程及环境信息；只把请求和项目事实提供给被评估的 AI，判据留给评审者。

比较版本时保持模型、工具、权限、项目和请求相同，按 [评测说明](README.md) 重复运行并保留失败及受阻情况。设计语义需要人工或独立评审，关键词、章节数和图数量不能作为通过依据。

## 1. 局部 CLI 修复

**请求与事实**：使用现有 `python-cli` 场景，要求修复 dry-run 写入目标文件的问题。已有项目入口、实现和测试，没有新增公共契约或数据模型需求。

**核对**：从已有代码和测试进入，验证目标文件保持原状及普通导入行为。无需新增需求目录或图，不因工作流升级重新接入项目。效果由外部行为验收判断，额外文档数量只作观察。

## 2. 事件关闭与通知设计

**请求与事实**：在临时项目提供如下已确认规则，要求只出设计：事件状态为处理中、已关闭；所属责任人可以关闭事件，其他用户拒绝；关闭原因必填；重复关闭不得产生第二条通知任务；关闭结果不依赖通知发送成功，通知失败保留为可重试任务。事件与通知任务存储在同一关系数据库，后台进程调用外部通知服务。重试次数、延迟和通知服务是否支持幂等尚未确定。

**核对**：设计明确权限、状态与重复请求规则，时序说明关闭与通知任务记录的一致性、异步发送及失败路径，ER 表达事件与通知任务关系并与去重约束一致。简单的两状态关系可以用转换表，不强制额外状态图。重试参数及外部重复发送风险列为待确认并说明影响，不编造服务承诺。验收覆盖越权、缺原因、重复关闭及通知失败，任务按可验证结果拆分。仅设计请求不能实施业务代码。

## 3. 无数据库的文件处理库

**请求与事实**：临时项目提供公共库现有入口 `parse(text)` 及调用方样例，要求设计新增迭代接口 `iter_records(stream)`，旧接口保持兼容。调用方负责打开和关闭输入流；遇到非法记录时抛出带行号的异常；不得把整个输入流一次性读取到内存。没有 HTTP、界面或数据库。

**核对**：围绕公开接口、资源归属、延迟读取、错误传播和兼容性设计，从消费方安排验证。引用可验证的流读取约束，不虚构性能数字；不添加无关的 Web、ER 或部署设计。跨层图是否需要取决于实际实现复杂度。

## 4. 中断续做与验证失败

**请求与事实**：从 `resume-cli` 场景准备副本：去重行为已经实现，后续 dry-run 修复未完成。交接注明去重的先前验证，当前工作区存在尚未验证的 dry-run 改动；提供可复现的失败输入。请求继续实现并验证。

**核对**：先核对任务、diff 和最近证据，再读取当前增量需要的设计。保留去重行为，修复并验证 dry-run，不照抄历史通过结论；失败或缺少环境不记完成。只在实际需要时加载技术章节，允许读取依赖设计和项目规范。外部 CLI 验收通过与交接记录准确性分别判断。

## 5. 设计内部矛盾

**请求与事实**：给评审会话一份待审设计，其中已确认规则为“重复关闭不产生第二条通知任务”，但时序描述每次关闭都插入通知任务，数据定义也没有去重机制；验收只覆盖首次关闭。要求评审并说明影响，不直接实施。

**核对**：指出规则、时序、数据约束和验收的具体矛盾，给出需要决策或修改的范围。能渲染的图、存在关联任务、看板检查通过均不能消除该矛盾。建议应允许符合项目约定的实现方式，不把某个数据库索引或事务方案当作唯一答案。

## 6. 技术假设与重新评估

**请求与事实**：提供离线合并记录的 Python 函数，按 name 去重并保留首次出现的整条记录及顺序。实现用列表逐条查重，没有数据库或外部服务，也没有性能基线和约定目标。用户怀疑需要换数据库或上队列，要求先核对路径、用本地合成数据验证判断，再给建议及其依据和重新评估条件。允许隔离实验，不修改业务实现、不引入依赖或外部服务。

**核对**：从实际路径和测量建立依据，不盲从数据库或队列假设；实验明确数据范围，核对优化建议是否保留去重语义。没有约定指标时不编造生产承诺；区分局部证据与真实负载，重要建议包含适用条件和重新评估触发。不得以实验授权代替正式修改授权。

## 7. 一份设计按需拆页

**请求与事实**：给出一份报表设计，其中月度查询和文件导出共用统计规则。导出详细列映射由另一位负责人单独评审。要求保留现有功能范围、验收和历史任务，并补充空月份的显示约定。

**核对**：从原设计定位共用规则和所有验收项。导出细节移到链接指向的专题页或在既有专题原地修改，规则只有一处维护。历史编号、证据和任务仍可追溯。检查现有看板和验收安排。包含实施时，从实际导出入口验证结果。

## 8. 跨工作区冷接手

**请求与事实**：用一个已交付部分功能的隔离项目，在另一工作区从可访问分支开始。交接同时有现行规则、已确认但未生效的规则和仅适用于旧提交的测试报告。给新会话项目入口和任务说明。另设缺少本地改动的变体。

**核对**：定位当前任务及可访问的提交，区分现行和待发布行为。说明历史证据是否覆盖当前改动，重跑受影响检查并保留已交付行为。缺少改动时准确报告缺口，继续独立工作，待取得改动再确认依赖项。

## 9. 用同一输入比较业务选项

**请求与事实**：一个本地导入工具准备支持批次文件。一份样例中，第一条记录有效，第二条无效。维护者正在考虑「整批回退」与「保留有效记录」，要求先比较后果，现有正常样例在两种方案下都成功。现有资料未约定失败后的重试或部分成功语义。

**核对**：围绕同一份正常样例和混合输入，验证两种方案下可观察的写入、退出结果和重跑影响。若使用独立原型，标明它只演示候选行为。聚焦部分成功是否可接受以及重跑需要满足的约束，给出带适用条件的建议。方案确认前保留现有行为。

## 10. 从空项目交接第一版开发约定

从空目录建立一个统计非空行的 CLI，提供可调用的库入口。首次未指定测试工具，由实施者选择并说明理由。第二轮给定新的测试文件命名约定，并要求显式开关可以计入空行。另有尚待决定的 JSON 输出建议。

用全新检出评审。接手者能否从项目入口找到现行命令，在不依赖上一轮会话的情况下，验证原有和新增行为？检查工具选择的来历、命名约定的适用范围和待定输出提案。分别记录真实用例、文档可复跑性以及是否观察过独立接手者。

复测历史证据的适用范围时，保留任务中“四项通过”的原始记录，仅在独立工作副本中让计数实现忽略新增开关。试验者先确认默认计数的两个入口通过、含空行的两个入口失败。给接手者一条只读评审请求，不透露改动或预期分数。另给只做材料评审的会话相同的项目文档，请它解释规范并说明交付依据。对照实际操作记录，分别核对规则理解、是否真实复跑和本次结果；执行受阻单列。

## 11. 同一项目启用工作流前后的接手对照

从同一提交建立两个独立工作区，保留相同的项目入口、开发规范、已确认设计、待办任务及旧实现。其中一份通过正常安装入口启用工作流。用户只说“继续完成季度月报导出，沿用项目约定，做好后给我看实际文件”。对照时核对项目文件摘要，记录工作流额外分发的入口提示与文件。

两组都从项目入口开始，自行选择要查阅的路径。记录每次请求，区别列出目录、读取规范和实际采用规范。分别从生成的 XLSX 核对业务口径、项目金额格式、原调用契约及季外兼容，并检查原任务是否写回当前结果和有效的产物位置。若宿主代理读写和运行验收，两组使用同一接口，报告中说明代理代办了哪些步骤。

如果差异出现在任务回写，可复用相同种子提交再做一次小对照。两组均沿用项目指引，只在其中一组的待办任务下增加一句：“收到验收结果后，请在本条任务下写明完成状态、实测结果，并链接实际工作簿和验收报告。”重新跑无提示组，观察同一配置是否也有波动。分别核对是否读到原任务、是否在验收后更新、引用的文件能否打开。

## 结果记录

每次记录场景、工作流版本或摘要、模型与工具环境、产物和过程位置、行为验收结果、语义评审结论及未验证项。仅在可观测轨迹支持时判断读取了哪些参考；不可观测时记为未知。区分任务失败、评审发现和环境受阻，不能把本文件列出的预期当作已完成的 AI 对照结果。

规则修改应关联实际发现：记录失败、对应改动和复测结果；没有暴露失败的规则不能宣称已证明必要。能通过删减提示或复用项目约定解决时，不继续叠加通用要求。
