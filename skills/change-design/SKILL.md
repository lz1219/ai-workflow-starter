# 需求设计与增量交付

先查项目级开发规范、目标模块差异及适用的重大技术决策，再对照本次目标和相关需求设计。缺少明文规范时，可从 README、构建、CI 和代表性实现起草首版，请人确认后再开发。已有规范直接沿用。只要求讨论时交付判断与建议。

## 和需求方谈到能做决定

技术事实用代码、样例或有边界的实验核对。修复已定义的行为沿用原验收；人已明确范围和最终效果的局部变更，更新原设计后可直接做。其余新设计取舍先给出方案、影响和验收样例，与人审查通过后实施。业务规则写回所属设计，其他设计引用对应小节或验收编号。

遇到会改变交付结果的分歧，用需求方熟悉的例子交谈：同一输入在两个方案下分别会看到什么，影响哪位使用者？给出自己的推荐及理由，把需要人决定的问题问具体。比如“按已填月份平均是 60，按整个季度平均是 40。财务要采用哪一个？”可以先推进的工作说明范围。回复的长短随问题而定。

确认后把规则、理由、适用范围和按选定口径重算的样例写回维护它的地方。尚待确认的选择单独标明来源和影响。需求方改主意时，找回原决定和依赖它的调用方，查清这次改变的是展示、业务规则还是生效范围；把影响说清后，只重新确认有分歧的部分。更新同一份设计，给历史交付保留适用版本。

## 进入实施或评审

- **实施、续做或验收**。核对原任务、验收项与当前改动。从目标模块查适用编码规范和参考实现，按 [小步实施与验收](references/implementation.md) 交付并写回结果。
- **设计评审或演进**。按契约、数据、交互和恢复风险选择 [技术章节](references/design-sections.md)。拆页、跨版本变更和需求关系参照 [需求演进](references/requirement-lifecycle.md)。

## 明确需求与现状

1. 从项目入口找到开发规范和需求索引。按工单号、业务关键词和同义名称搜索已有需求，交叉核对调用入口、契约、代码及链接。结合 PR、部署记录或已发布契约判断交付状态。能唯一匹配时直接复用，多个合理候选影响范围时才询问。无法证实的状态标记待确认。
2. 提取目标、角色、规则、限制和本次不做的内容，区分已覆盖、已有需求变更和新能力。较长需求按可独立交付和验收的业务结果拆解，记录依赖。同一结果涉及多个模块时共用设计；跨仓库沿用主责或共享文档位置，各任务或 PR 引用同一主设计和验收编号。
3. 区分当前行为、已确认要求和方案建议。用代码路径、契约、测试或用户决定说明依据，关键未知保留为待确认，不编造性能指标、重试规则或业务权限来补齐模板。

## 设计与评审

- 需要独立设计时沿用项目目录约定；缺少约定时用 [设计模板](assets/design.md) 创建 `docs/design/Req-YYYYMMDD-需求名称/design.md`。只保留适用小节。日期、稳定路径和后续演进按 [需求演进与索引](references/requirement-lifecycle.md) 处理。
- 一份设计默认用小节组织。某部分的契约、取舍或风险需要单独查阅或评审时，从原 `design.md` 按需链接专题页。共用验收编号和任务记录，具体规则各有一个维护位置。
- 用正常、失败和边界场景描述可观察结果，验收项使用稳定的 `AC-*` 编号。按 [技术章节与图示选择](references/design-sections.md) 展开受影响的流程、状态、数据、契约和风险。图放在对应设计小节，长契约或附件由主文档链接。
- 用 [任务模板](assets/tasks.md) 记录可独立验证的增量，使用 `T1`、`T2` 等稳定编号关联验收项。一项可以包含接口、数据和测试；探索或工程准备任务也应有可核对的结果。保留已完成记录。
- 评审时核对业务规则、图、契约、数据约束、任务和验收是否一致。图语法正确、任务覆盖完整都不能证明方案正确。交付关键取舍、未决项和受影响范围；反馈更新同一文档的「待确认与决策」。
- 公共契约、存量数据、跨模块边界、长期运维责任或难以撤销的新选择，在依赖它的实现前共同审查。已有技术决定适用时直接引用；新决定记录依据、适用条件及何时重评。普通实现细节不增加决策记录；重评不自动授权替换方案。

## 实施与完成标准

按“选择结果 → 确定验证方法 → 实现 → 验证 → 记录证据 → 下一项”推进。每项通过后按已有授权继续；失败时先判断原因，依赖失败结果的任务不能视为前置条件已满足。具体续做、阻塞和证据规则见 [小步实施与验收](references/implementation.md)。

任务完成需要对应范围的实际结果。仅有命令、PR 链接或文字声明不足以证明通过。区分已安排、通过、失败和等待条件；局部测试不能替代跨模块验收。交付前核对当前改动上的证据，代码或契约变化后重新判断历史结果是否适用。

采用本模板时，按 [需求演进与索引](references/requirement-lifecycle.md) 刷新或检查看板。`--review` 检查验收安排覆盖。重新评审已确认的设计时，可加 `--base <上次确认的提交>` 查看验收条目变化及关联任务，再判断哪些结果需要复验。发布时把长期有效的行为和契约同步到项目已有规格或 API 定义。
