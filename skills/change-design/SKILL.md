# 需求与技术设计

用户可以直接用自然语言描述想实现的功能。沿用项目的需求目录约定。缺少约定时用 [设计模板](assets/design.md) 创建 `docs/design/Req-YYYYMMDD-需求名称/design.md`，例如 `Req-20261111-运维事件登记与关闭`。日期用需求设计首次建立的本地日期，需求名称使用团队日常语言。已有工单编号或来源时记录在文档顶部。目录路径一旦用于关联，就作为稳定标识。

## 1. 读项目和明确需求

1. 从 `AGENTS.md` 找项目概览、开发规范和需求索引。按工单号、业务关键词和同义名称搜索需求标题与正文，并交叉核对接口、表名、相关代码和已有链接。结合 PR、部署记录或已发布契约判断交付状态。能唯一匹配时直接使用对应设计，只有多个合理候选会影响范围时才请用户确认。状态无法证实时标记待确认。
2. 收到一大段需求时，提取原始目标、角色、规则和限制，检查哪些已覆盖、哪些是对已有需求的变更、哪些是新需求。按可独立交付和验收的业务结果拆解。共同构成一个结果的页面、接口、数据表和测试写在同一需求的实施计划里。给出拆解结果、顺序、依赖和需要确认的业务边界，再为范围清楚的需求起草设计。
3. 把用户明确给出的规则写进「需求与验收」，技术方案写进设计部分，提议与已确认事实分别标明。对会改变业务语义、接口承诺、数据含义或上线风险的未决项，列出建议和影响。

## 需求关系和索引

- `depends_on` 表示依赖的业务能力，`follows` 表示独立需求演进自哪份设计，`related` 表示可独立推进的关联需求。若本次任务必须等另一个增量，在 `tasks.md` 记录具体任务、PR 或接口条件。
- `design.md` 头部保存标题和关系，关系字段填稳定目录名。评审、实施和验收按本次增量记录。总看板汇总任务状态、已完成增量和需求关系，并列出阻塞任务及其交接信息。
- 项目已有 Issue 看板时沿用，仓库索引引用对应来源。采用本模板的项目可把本 Skill 随仓库保存，并在开发规范记录从仓库根目录执行的命令。例如 `python .agents/skills/change-design/scripts/requirements.py --write` 刷新 `docs/design/README.md`，把 `--write` 换成 `--check` 可检查任务、关系和看板时效。个人安装时用 Skill 下脚本的路径并显式传入 `--project <项目根目录>`。

## 2. 交付设计草案

- 用业务场景、失败场景、边界条件和可验证的验收项定义交付范围。每条验收项保留稳定编号，例如 `AC-1`。
- 用 Mermaid 时序图表达关键调用，覆盖重要的失败或分支。参与者与实际代码或计划新增的模块对应。涉及业务状态时按需补状态图。
- 涉及业务数据或持久化时，用 Mermaid ER 图标明关系和基数，同时写清表字段、类型、可空性、默认值、主外键或逻辑关联、唯一约束、索引和查询用途。数据结构有变化时说明 Flyway 版本、兼容或回填、验证与恢复。ER 图与表定义使用一致的表名和键。
- 涉及接口时，写清方法、路径、请求字段和校验、返回字段、HTTP 状态、错误、分页或幂等。给出关键请求与响应示例，关联验收项。已有 OpenAPI 契约时链接并写清变更。
- 无 HTTP 接口、数据关系或迁移时，在对应小节简短说明适用范围，例如「读取现有表，无结构变化」。图和字段按项目实际设计填写。
- 用 [任务看板模板](assets/tasks.md) 在设计同目录建 `tasks.md`。按本次改动拆出可验证的增量，编号用 `T1`、`T2`，与 `AC-*` 关联。后续按顺序追加任务，保留已完成记录。
- 自审接口、时序、ER、字段类型和验收条件是否一致。交付本次评审范围、设计与任务看板、需决定的问题和主要取舍。验证计划写明预期，执行结果等实现后填写。刷新需求总看板。

## 3. 评审、实现与验收

1. 用户反馈直接更新同一份文档，把重要决定、日期及来源写进「决策和变更记录」。明确区分哪些问题已确认，哪些仍开放。
2. 用户确认可实施后，记录确认范围和对应任务编号。若用户明确要求同时设计与实现，且关键决策已经给定，可以依授权继续。项目的高风险评审规则仍适用。
3. 开始实施或切换会话时，读当前设计、`tasks.md`、关联任务和 Git diff。开始、阻塞或完成时更新对应任务。若隔离测试已通过，而正式验收要等上游接口、数据或权限，可独立验收的本地工作记为完成，剩余验收单列阻塞任务，写清前置条件及已有证据。仍有可推进工作时保留进行中。任务变化后刷新总看板。
4. 实现后按验收项记录已验证场景、环境、命令和结果，列出仍待验证的场景及条件。例如隔离测试通过后，正式数据的字段映射与对账仍需单独验收。PR 引用设计和对应任务，任务记录实际内容、证据和 PR 或提交。长期有效的行为和契约同步到项目已有规格或 API 定义。

## 4. 后续需求变更

| 当前情况 | 文档怎么改 | 开发怎么继续 |
|---|---|---|
| 同一业务能力正在评审或开发 | 更新原设计的本次方案。调整受影响的未完成任务、图、接口和验收项，记录重要决定。 | 业务语义、公开契约、数据含义或上线风险发生变化时，确认受影响的部分。 |
| 同一业务能力继续迭代，相关行为已经交付 | 在原目录追加任务。用实际交付版本作为基线，在设计里写清本次增量、兼容影响和验收。 | 实施后保留原任务和验证记录，更新生效规则，验证数据升级和回归。 |
| 新增可独立维护的业务能力 | 建立新的具名需求目录，按实际关系引用已有能力。 | 单独设计、评审和验收。 |
| 修复实现偏差，目标仍是已确认的行为 | 在 Issue 或 PR 链接原验收项，记录复现和验证。若重新定义预期行为，按需求变更处理。 | 补回归测试并验证原承诺。 |

验收项保留稳定编号。规则被替换时保留原编号并标明后继验收项，新增验收用新编号。已在目标环境执行的 Flyway 迁移保持原文件，通过下一版本演进。独立维护的 OpenAPI、原型或其他附件可放在需求目录内，由 `design.md` 链接。发布时同步项目已有的长期规格或接口契约。
