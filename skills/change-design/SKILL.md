# 需求设计与增量交付

把业务目标、方案和实际验收关联起来。先读项目 `AGENTS.md`，沿用项目规范、现有设计和验证入口。用户只要方案时交付方案；已明确要求实施且关键决策已给定时，在授权范围内连续推进。只确认会实质改变范围、业务语义、契约、数据含义或上线风险的未决问题。

## 选择当前入口与工作量

这是具体变更的入口，日常变更不必重新运行项目接入。按当前任务读取需要的参考，已有设计可直接进入实施或验收。

先判断阻碍当前结果的未知，再选择动作，不要求每次从设计开始或走完所有步骤：

| 当前缺少的依据 | 下一步 |
|---|---|
| 要解决的问题或成功条件不清楚 | 核对使用场景和现有能力，只询问会影响结果的目标与取舍。 |
| 不知道系统实际行为或故障原因 | 探查、复现或测量，先取得事实。 |
| 关键技术假设尚未证实 | 做有边界的最小实验，记录假设、观察结果及对方案的影响；按 [技术章节参考](references/design-sections.md) 控制范围。 |
| 预期和实施路径已清楚 | 实现一个可验证增量；协作关系不确定时补契约检查或联调。 |
| 功能正确，但实际收益未验证 | 在已授权范围内核对使用结果；没有观察条件就说明效果未知，不扩大到生产操作。 |

已有配置或能力足以解决问题，或实验否定原方案时，提出复用、缩减或停止该路线的依据，不自行改变用户目标。新证据出现后可以返回探查或修订方案；不为完成流程继续无效实施。

| 当前任务 | 做法与按需读取的资料 |
|---|---|
| 预期清楚、影响局部的修复或调整 | 在当前任务、Issue 或 PR 记录预期、简短方案和实际验证，沿用项目开发流程。已有验收项就引用，无需新建设计目录、任务表或总看板。 |
| 需要拆分实施、有关键取舍或跨模块的功能设计、设计评审 | 按下文明确需求，再读 [技术章节与图示选择](references/design-sections.md)。编写设计时创建或补充设计与任务；仅评审时输出发现、影响和建议。 |
| 按已有设计实施、中断续做或验证交付 | 先核对当前任务、验收项和 Git diff，再读 [小步实施与验收](references/implementation.md)。只展开当前增量涉及的设计和依赖。 |
| 新建需求目录、建立需求关系、维护看板或调整已有需求 | 读 [需求演进与索引](references/requirement-lifecycle.md)，复用稳定目录和编号。 |

涉及公共契约迁移、权限或租户边界、历史数据改写、难以回退的发布时，补充兼容、发布与恢复安排，遵循项目高风险评审规则。调查发现影响扩大时再升级流程，并说明新增风险或决策。轻量变更同样需要验证实际行为。

## 明确需求与现状

1. 从项目入口找到开发规范和需求索引。按工单号、业务关键词和同义名称搜索已有需求，交叉核对调用入口、契约、代码及链接。结合 PR、部署记录或已发布契约判断交付状态。能唯一匹配时直接复用，多个合理候选影响范围时才询问。无法证实的状态标记待确认。
2. 提取目标、角色、规则、限制和本次不做的内容，区分已覆盖、已有需求变更和新能力。较长需求按可独立交付和验收的业务结果拆解，记录依赖。同一结果涉及多个模块时共用设计；跨仓库沿用主责或共享文档位置，各任务或 PR 引用同一主设计和验收编号。
3. 区分当前行为、已确认要求和方案建议。用代码路径、契约、测试或用户决定说明依据，关键未知保留为待确认，不编造性能指标、重试规则或业务权限来补齐模板。

## 设计与评审

- 需要独立设计时沿用项目目录约定；缺少约定时用 [设计模板](assets/design.md) 创建 `docs/design/Req-YYYYMMDD-需求名称/design.md`。只保留适用小节。日期、稳定路径和后续演进按 [需求演进与索引](references/requirement-lifecycle.md) 处理。
- 用正常、失败和边界场景描述可观察结果，验收项使用稳定的 `AC-*` 编号。按 [技术章节与图示选择](references/design-sections.md) 展开受影响的流程、状态、数据、契约和风险。图放在对应设计小节，长契约或附件由主文档链接。
- 用 [任务模板](assets/tasks.md) 记录可独立验证的增量，使用 `T1`、`T2` 等稳定编号关联验收项。一项可以包含接口、数据和测试；探索或工程准备任务也应有可核对的结果。保留已完成记录。
- 评审时核对业务规则、图、契约、数据约束、任务和验收是否一致。图语法正确、任务覆盖完整都不能证明方案正确。交付关键取舍、未决项和受影响范围；反馈更新同一文档的「待确认与决策」。
- 重要决定记录依据、适用条件或关键假设，以及什么变化需要重新评估。普通实现细节不增加决策记录；重评不自动授权替换方案。

## 实施与完成标准

按“选择结果 → 确定验证方法 → 实现 → 验证 → 记录证据 → 下一项”推进。每项通过后按已有授权继续；失败时先判断原因，依赖失败结果的任务不能视为前置条件已满足。具体续做、阻塞和证据规则见 [小步实施与验收](references/implementation.md)。

任务完成需要对应范围的实际结果。仅有命令、PR 链接或文字声明不足以证明通过。区分已安排、通过、失败和等待条件；局部测试不能替代跨模块验收。交付前核对当前改动上的证据，代码或契约变化后重新判断历史结果是否适用。

采用本模板时，按 [需求演进与索引](references/requirement-lifecycle.md) 刷新或检查看板；`--review` 仅检查验收安排覆盖，不验证设计语义或实际行为。发布时把长期有效的行为和契约同步到项目已有规格或 API 定义。
