# 小步实施与验收

按设计实施、续做或验证交付时读取。已确认的范围内连续推进，不把每个增量变成一次用户审批；仅设计请求停在方案，高风险变更遵循项目评审要求。

## 开始或恢复

先核对用户已授权的范围、当前任务、关联验收项、Git diff 和最近验证结果，再读该增量涉及的契约、设计及依赖。记录与代码不一致时查明差异，不因任务标记完成就跳过，也不重复覆盖已经交付的行为。

只有影响当前结果的未决项需要先解决。未知来自技术事实时先探查、复现或做有边界的实验；来自业务取舍时才请求确认。其他开放问题记录在设计中，独立且已授权的工作可以继续。

## 每个增量的闭环

1. **选择结果。** 取一个边界清楚、能验证的任务，明确依赖和完成范围。例如「按部门筛选后，CSV 只含该部门的数据」。接口、业务逻辑和测试可以属于同一项，无需按代码层强拆。探索任务交付可复现的调查结论或取舍依据。
2. **确定验证方法。** 引用验收编号，明确输入、预期结果、实际工作目录和环境。缺陷先复现；其他变更沿用相关基线。复现或基线受阻时记录原因，不伪称已有失败证据。
3. **实现并验证。** 执行覆盖当前行为和相关回归的最小有效检查。失败时区分实现问题、已有失败和环境问题；修复后重跑受影响检查。依赖失败结果的任务不得推进为已满足前置条件，独立任务可以继续。
4. **记录再推进。** 把实际改动、验证范围与结果写回任务，附可定位的证据，再依据结果选择下一项或返回调查。实验否定假设或触发重要决定的重评条件时，重新判断方案，不机械推进依赖它的任务。不要求每步提交 Git 或运行全量测试。发现业务语义、契约或风险实质变化时，更新受影响设计并按授权及项目规则处理。

任务粒度以可核对结果为准，不用固定时长、文件数或 token 数切分。一个任务包含多个无法分别判断的结果时，再拆成能分别验证的增量。

## 证据、阻塞和交接

证据记录场景、环境、命令或操作步骤、预期与实际结果，以及对应提交或未提交改动的范围。日志较长时链接测试报告，不复制敏感数据。命令描述验证方法，PR 定位改动；两者本身都不证明通过。

任务状态沿用「待办、进行中、阻塞、完成、取消」，验证结果另在证据栏说明：已安排、通过、失败或等待条件。环境不具备时保留未验证状态；失败不可写成完成。

隔离实现与正式验收可以独立交付时，拆成两个任务。已通过的本地工作可标完成，正式接口、数据或权限未就绪的验收任务标阻塞，写明恢复条件，整体交付仍说明未完成验收。

暂停时记录最后实际验证的状态、剩余问题、下一步及所需条件。采用仓库看板时，任务变化后刷新总看板；命令见 [需求演进与索引](requirement-lifecycle.md)。

## 整体验收

交付前核对所有本次验收项的实际结果，并执行受影响的联调、契约或项目要求的完整检查。局部通过不能替代端到端验证；代码、契约或环境变化后，按证据对应的范围重新判断适用性，补跑受影响检查。无关提交不自动使全部证据失效，影响不明时标记需核对。

功能验收与实际收益分别说明。已有业务目标且允许观察时，可用用户试用、操作前后对比或适当样例核对效果；缺少条件则明确尚未验证，不扩大到生产数据、部署或额外监控。

PR 引用设计和任务，任务保留实际内容与证据。明确哪些通过、失败、等待条件，以及它们对交付的影响。长期有效的行为与契约同步到项目已有规格或 API 定义，保留历史验收的适用版本。
