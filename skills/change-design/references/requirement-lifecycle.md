# 需求演进与索引

新建需求目录、建立关系、维护看板或调整已有需求时读取。仅实施某个已确定任务时，按需查阅这里的命令，不必重新组织全部需求。

## 目录与关系

沿用项目已有的需求记录和 Issue 看板。缺少约定时，独立设计位于 `docs/design/Req-YYYYMMDD-需求名称/design.md`，日期使用首次建立的本地日期，名称使用团队日常语言，例如 `Req-20261116-运维事件登记与关闭`。工单编号或来源记录在顶部，路径一旦用于关联即保持稳定。

`design.md` 头部保存标题和关系，关系字段填稳定目录名：

- `depends_on`：依赖的业务能力。
- `follows`：独立需求演进自哪份设计。
- `related`：可独立推进的关联需求。

本次增量若必须等待另一个增量，在 `tasks.md` 写具体任务、PR 或接口条件。跨模块共用主设计和验收编号，跨仓库沿用已有主责或共享位置，各仓库记录自己的实现与验证。

## 拆任务、设计拆页或拆需求

| 判断 | 做法 |
| --- | --- |
| 同一方案，实施有多个可验证增量 | 保留一份设计，拆分任务。 |
| 共用一个业务目标，局部场景的契约、取舍或风险需要单独查阅或评审 | 先用小节组织。独立维护确有收益时，从原 `design.md` 链接具名专题页。 |
| 各自满足独立业务目标，可单独交付和维护 | 各建主设计，按实际依赖或演进关系关联。 |

拆页保持同一份设计。原 `design.md` 保留目标、共用规则、边界、跨部分依赖、整体验收和专题入口。缺少路径约定时，可把局部细节移到同一需求目录的 `design/<场景>.md`，在原位置保留链接。专题页回链主设计，说明适用范围、局部决定和验证方法。比如统计口径留在主设计，XLSX 列映射单独放在导出页，两处用链接关联。

采用本仓库的看板工具时，验收编号及可观察预期在原 `design.md` 的「需求与验收」表集中定义。专题页引用相关 `AC-*`，补充技术细节、案例和验证方法。所有增量仍进入原 `tasks.md` 或项目已有的主任务入口。有联动时补跨部分的验收，评审者核对主入口和受影响的专题页。

## 后续需求怎么改

| 当前情况 | 记录与推进方式 |
|---|---|
| 同一能力正在评审或开发 | 更新原设计中维护该规则的章节或已链接专题页，核对受影响的验收、图、契约和任务。业务语义、公开契约、数据含义或上线风险改变时，确认受影响部分。 |
| 同一能力继续迭代，相关行为已经交付 | 小调整直接更新原设计的对应位置，按需追加原任务。并行变更或多个发布版本可用关联工单、PR 或版本说明记录各自差异，注明生效条件。 |
| 新增可独立维护的业务能力 | 新建具名需求目录，按实际关系引用已有能力，单独设计、实施和验收。 |
| 修复实现偏差，目标仍是已确认行为 | 引用原验收项，在原任务、Issue 或 PR 记录复现与回归结果。 |
| 无对应设计的局部变更 | 沿用工单、PR 或提交说明记录预期、改动和结果。需要后续接手时，在团队可访问的现有记录留下一步及恢复条件。 |

当前生效规则与已确认但尚未生效的方案都可从原设计找到。重要变化记录确认来源、适用版本或启用条件。代码、契约、测试和设计说法不同时，先核对各自适用范围并查证实际行为，再确定需要修复的对象。交付后将生效规则同步到已有规格或契约。

保留已合并的验收和任务编号。替换规则时注明后继项、旧规则适用版本及历史证据。并行变更合并前核对目标分支。新增编号重合时，为尚未合入的条目换号并同步引用。若同一规则在不同变更中的预期冲突，先确定合并后的行为，再重新检查受影响的验收，按合并后的任务刷新看板。

## 看板与检查

已用 Issue 看板的项目沿用原来源，仓库索引保留链接。采用本模板且将 Skill 存于 `.agents/skills/` 时，在项目根目录执行：

```sh
python .agents/skills/change-design/scripts/requirements.py --write
python .agents/skills/change-design/scripts/requirements.py --check
python .agents/skills/change-design/scripts/requirements.py --review "Req-YYYYMMDD-需求名称"
```

`--write` 刷新 `docs/design/README.md`，汇总任务、已完成增量、关系和阻塞信息。`--check` 检查任务、编号、关系与看板时效。`--review` 检查主设计中的验收项是否有关联任务或书面验证安排。专题链接、细节和一致性由评审核对，实际验证另行执行。

初次生成时，脚本自动标出看板区域。已有手写索引时，在希望插入看板的位置加入下面两行 HTML 注释，放在代码块外。刷新只更新两行之间的内容，发布说明、Issue 链接和其他团队记录放在区域外。

```md
<!-- ai-workflow:board -->
<!-- /ai-workflow:board -->
```

旧版纯生成看板会在下次刷新时补上标记。如果原看板混有手写章节，先用这两行圈定原有生成内容。任务行在同一张标准任务表内连续排列。脚本汇总独立需求的报错，并按行定位同一份任务记录中可识别的重复表头、表外任务和字段错误。按反馈修正后再运行检查。有格式或引用错误时，`--write` 保留现有看板。

复审已有需求时，可在 `--review` 命令后追加 `--base <上次确认的提交或标签>`。工具读取 Git 中同一路径的验收表，与当前工作区按编号对照，显示变化前后的单元格和当前关联任务。基准缺少该路径时当前条目均显示为新增。文字润色也会显示；由评审者判断行为是否变化、哪些旧结果还能沿用。正文、专题页和契约仍按本次影响范围阅读。

位于其他仓库内且未被其跟踪的源码快照可直接使用 `--review` 检查验收安排。有 Git 历史的子项目可引用跟踪它的仓库提交。

实际安装目录不同时替换脚本路径；个人安装使用 Skill 下脚本的路径并显式传入 `--project <项目根目录>`。将项目采用的命令保存在开发规范，任务变化后更新看板。
