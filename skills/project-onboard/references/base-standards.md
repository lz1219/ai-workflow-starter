# 基础开发规范

按本次改动的影响范围应用这些规则。确定项目规范时，用真实代码、工具配置和已确认的契约替换抽象建议。

已有工程按目标目录区分三类依据：有效配置与维护者已确认的要求可作为约束；多处一致的实现可作为参考；工作流提供的做法可作为建议。新项目先沿用团队基线，缺少约定时由 AI 为首个可运行场景选取可逆的默认做法，说明选择。涉及公共契约、依赖策略等长期取舍时交由维护者定案。一次需求中的例外只在相应范围生效。

## 第一版规范的形成与修订

新项目明确首个交付场景后、编写依赖这些决定的代码前，AI 先起草一版。只写眼下会用到的内容，例如代码放在哪里、一个关键边界由谁负责、从哪里验证。已有团队标准直接链接并注明适用范围。没有单独文档的小项目可在 README 或 AGENTS.md 中放几行。

- **人只要方案或明确要求先审**。展示草案和 AI 的建议，等待反馈后再实施。
- **已授权创建或开发**。告诉维护者本轮准备采用哪些可逆默认值及理由，随后推进首个增量。影响公开契约、历史数据、团队长期维护成本，且现有授权或规范尚未决定的取舍，给出备选、推荐及后果，在依赖它的实现前确认。可独立推进的部分继续。
- **首个增量跑通**。把实际工作目录、执行命令及验证范围写回项目入口。保留默认项的来历；测试通过说明这套做法可用，维护者采纳后才将相应建议记为团队约定。若维护者调整草案，检查已经生成的代码、配置和测试是否也需同步。

例如，一个新 CLI 可以先按可逆默认值将测试放在 `tests/`。若它要供定时作业调用，部分导入失败的退出码会决定作业是否重试；缺少既有契约时，将该问题写入需求设计，请维护者选择。第一次测试运行后，把实际命令补到开发指引。

老项目缺少成文规范时，从当前任务涉及的配置、调用方和代表性实现取证，在首次接入或遇到具体缺口时补写。沿用项目自己的评审方式。配置迁移、维护者决定或例外需要跨需求复用时，再修订相应规则，说明适用模块和生效条件。

## 按影响选用的基础约定

| 主题 | 基础约定 | 验证方式 |
|---|---|---|
| 范围与兼容 | 保持现有调用方依赖的行为。新增或变更公共接口、事件、数据格式时，识别调用方与版本影响。 | 契约测试、调用方验证或设计评审。 |
| 输入与权限 | 在可信服务端边界校验输入、资源归属和访问权限。明确空值、重复请求和非法状态的处理。 | 正常、非法、未授权和越权场景。 |
| 错误与日志 | 沿用项目错误语义，保留可定位的失败信息，保护凭据和敏感数据。 | 失败路径测试，必要时检查日志输出。 |
| 数据与副作用 | 明确事务、并发、重试、幂等与部分失败语义。金额和时间按业务约定处理精度、单位和时区。 | 边界、重复执行、回滚或迁移校验。 |
| 可维护性 | 沿用项目命名、模块边界和现有约定。确实需要新增依赖或模式时说明原因和影响。 | 项目已有的格式、静态检查、架构检查和代码评审。 |
| 测试与交付 | 缺陷重跑原始复现，新增或改变行为覆盖关键场景。记录真实运行的命令、结果和剩余验证。 | 本地运行相关检查，CI 运行项目要求的检查。 |

工具可以验证格式、构建、测试或明确的契约。评审者判断业务语义、设计取舍和回滚是否合适。
