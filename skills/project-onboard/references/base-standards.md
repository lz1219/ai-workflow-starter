# 基础开发规范

按本次工作查项目级开发约定、目标模块的差异和重大技术决策。有效配置说明工具实际执行什么；代码中重复的写法说明项目惯例；AI 提出的默认做法要标为建议。需求的业务口径维护在所属设计，其他设计引用该处。

## 第一版规范的形成与修订

新老项目都先形成项目级约定，再按需补充模块差异。已有适用规范就核对并沿用。缺少明文规范时，先起草并请人确认，再开始依赖它的开发。新项目依据团队标准、技术栈与首个交付目标；老项目依据构建、CI、代表性代码、测试和已有技术决定。可把首版和首个需求设计一起审；影响设计方向的缺口先讨论，局部可逆的建议可以随设计确认。开发授权本身不能说明人已经认可新起草的规范。

- **写到能指导一次改动。** 说明作用范围、具体做法和依据。硬约束用“必须”；团队偏好用“通常”，有工程理由可在本次调整，交付时简述原因。模块只写与项目约定的差异。观察到的偏差若要成为硬约束的例外，引用已有决定或请人确认适用范围。
- **判断重大技术选择。** 先引用适用的已有决定。新选择影响公共契约、存量数据、跨模块边界、长期运维责任或难以撤销时，在依赖它的开发前共同评审方案、理由和后果。工程决定留在开发指引或已有架构决策记录，相关设计引用。
- **改进和维护。** 新增、收紧或放宽开发要求时，与人确认生效范围，默认应用到新增和本次直接受影响的代码；存量迁移另行决定。核实后可直接修复链接、同步已确认的事实或澄清原意。变更测试命令时实际运行它，核对测试发现结果，再更新原入口。小项目可在 README 或 AGENTS.md 中维护这几条约定。

## 按影响选用的基础约定

| 主题 | 基础约定 | 验证方式 |
|---|---|---|
| 范围与兼容 | 保持现有调用方依赖的行为。新增或变更公共接口、事件、数据格式时，识别调用方与版本影响。 | 契约测试、调用方验证或设计评审。 |
| 输入与权限 | 在可信服务端边界校验输入、资源归属和访问权限。明确空值、重复请求和非法状态的处理。 | 正常、非法、未授权和越权场景。 |
| 错误与日志 | 沿用项目错误语义，保留可定位的失败信息，保护凭据和敏感数据。 | 失败路径测试，必要时检查日志输出。 |
| 数据与副作用 | 明确事务、并发、重试、幂等与部分失败语义。金额和时间按业务约定处理精度、单位和时区。 | 边界、重复执行、回滚或迁移校验。 |
| 可维护性 | 沿用项目命名、模块边界和现有约定。确实需要新增依赖或模式时说明原因和影响。 | 项目已有的格式、静态检查、架构检查和代码评审。 |
| 测试与交付 | 缺陷重跑原始复现，新增或改变行为覆盖关键场景。记录真实运行的命令、结果和剩余验证。 | 本地运行相关检查，CI 运行项目要求的检查。 |

工具可以验证格式、构建、测试或明确的契约。评审者判断业务语义、设计取舍和回滚是否合适。
