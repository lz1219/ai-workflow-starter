# 接入探查与交付

接入已有项目或复查开发指引时读取。先看[覆盖范围](README.md)确认目标技术栈是否已有参考；默认先确认仓库级构建和模块边界，再沿目标模块的一条真实链路查到入口、规则及测试。根据需解决的问题扩大范围，重复接入优先核对发生变化的模块、命令和证据。

## 取得证据

1. 从根和目标模块的 `AGENTS.md`、`CLAUDE.md`、README、贡献指南和已有说明进入。根据构建清单、锁文件、模块声明及 CI 工作目录核对运行时、模块和入口。沿用项目现有 Wrapper、工具链和 CI 命令。
2. 根据项目形态追踪界面、HTTP、CLI、公开库、消息或任务。跨模块时标出边界、共享契约和各自入口。关键判断附路径、符号、配置或可复现结果。
3. 核对目录、工具版本、开关和测试资源后执行适用验证。记录编译或打包、实际测试及覆盖范围、跳过项。区分已知失败、依赖解析失败、环境未准备和实际新增失败。

## 未知技术栈

没有对应[参考](README.md)时，不要套用其他技术栈的结论。按下面的顺序探查，并在交付中说明哪些是已证实、哪些等待维护者确认：

1. **盘点工程事实。** 找到构建清单、锁文件、模块或工作区声明、运行时约束和 CI。记录实际工作目录和可用命令。
2. **跑通基线。** 执行项目已有构建和测试命令，记录结果、跳过项和缺失环境。不要先改代码再判断基线。
3. **走一条真实链路。** 从界面、HTTP、CLI、公开库、消息或任务入口追到实现和测试，记录入口、规则和验证边界。
4. **起草最小约定。** 只写能指导本次改动的 3–5 条，每条附路径、命令、测试或维护者决定；其余列为待确认。
5. **留下补充入口。** 按[参考模板](_template.md)记录覆盖内容、命令、陷阱和待确认项；需要长期使用时在覆盖表中增加一行。

时间盒由本次任务决定。只要求探查时交付草案和未决问题；已确认范围后再落地。维护者无法提供入口、文档或环境时，把缺口写进交付，不要用推测补齐。

## 交付摘要

用[接入报告模板](../assets/onboarding-report.md)交付单页结论，详细证据链接到项目文档。报告至少包含：

| 事项 | 说明 |
| --- | --- |
| 结论 | 能否按现有约定安全改动、最大风险、建议的下一步。 |
| 范围及基线 | 提交或当前工作范围、涉及模块、已走通的链路、未覆盖项。 |
| 已证实约定 | 3–5 条能指导本次改动的约定，每条附路径、命令、测试或维护者决定；其余列待确认。 |
| 项目入口 | 模块职责、运行时、构建根目录、代表性代码和验证入口。 |
| 实际验证 | 命令、执行目录、开关、实际结果及不能验证的条件。 |
| 待确认清单 | 来源、影响、需要谁确认和临时处理。 |
| 归处与后续 | 已复用或拟修改的文档，待跟进问题的负责人和恢复条件（已知时）。 |

首次接入的完成标准不是“文档写完”，而是上述报告可核对：约定有证据、基线实际跑过、真实链路走通过、未决项有归属。约定可以先写最小集，其余作为待确认项逐步补充；不要为凑齐文档而填入未经证实的规则。

每次接入在交付说明或接入 PR 给出结论。只有冲突、未决事项或分批接入需要持续跟踪时才长期保留接入记录。优先使用已有接入文档或工单，缺少位置时可建 `docs/onboarding.md`，由项目入口链接需要继续处理的事项。已有看板按项目约定维护。

把经证实的入口和命令提取到开发指引。重复出现的实现做法先记录为现行行为，团队规则、可执行约束或维护者决定支持时再作为长期约定。代码、测试、契约和说明冲突时保留双方证据及适用范围。可从项目证实的事实直接核对，涉及长期规则取舍再找对应维护者确认。需求口径由所属设计维护，其他设计按需引用。若项目缺少明文开发规范，交付首版草案并请人确认后再实施。

对会影响后续验证的关键事实，附决定实际行为的配置点和复核方法。例如分别记录项目默认 profile 与 CI 命令的跳测条件。改动相关配置时，核对有效设置并重跑受影响的入口，再同步规范。文件变化可以提示复查，是否过期由可观察结果判断。
